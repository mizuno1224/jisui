# jisui(自炊と暮らしの管理)

## これは何か

夫婦2人の暮らしの記録。**同じデータをスマホアプリと共有している。**

| やること | どこでやるか |
|---|---|
| 買い物中のチェック、在庫の増減 | **アプリ**(片手で1タップ。オフラインでも動く) |
| 予定・家事のチェック | **アプリ**(カレンダーで見る) |
| レシート20点の一括登録 | **ここ**(写真1枚で金額込み全件が入る) |
| カード明細CSVの一括取り込み | **ここ**(`import_card_csv`。辞書で費目を付ける) |
| 献立の相談・レシピ生成 | **ここ**(会話で条件を足していける) |
| 好み・NG食材の登録 | **ここ**(会話の流れで自然に拾える) |
| 月次の振り返り | **ここ**(数字を並べて考える作業に向く) |

アプリで入れた在庫はここから見えるし、ここで入れたレシピはアプリに出る。

## まとめて読む3つの入口

用途ごとに、必要なものが一度で揃うようにしてある。手元の記憶で答えず、まずこれを呼ぶ。

```python
j.context()              # 献立を考える: 在庫・常備品・好み・器具・調理履歴・買い物リスト
j.week("2026-08-10")     # 予定を見る: その週の献立・予定・家事・家事の記録
j.money("2026-08")       # 家計を見る: その月の支出・収入・予算・資産と負債
j.investments()          # 投資を見る: 保有銘柄・監視銘柄・直近の指標・資産の内訳
j.outlook()              # 将来: ローン残高の予定・俸給表
j.find_events("歯医者")  # 予定を探す: 題名・メモ・場所・持ち物を横断で
j.todo_tree()            # やること: 親子の入れ子で
```

**お金の話の前に `C:\\Users\\mmizu\\jisui\\方針.md` を読む。**
住宅ローンの条件、投資方針、そして「どの支出をどのカードで払うか」の
決めごとが書いてある。DB には入っていないので、読まないと毎回ずれた答えになる。

**家計簿の作法は KAKEIBO.md に分けてある。** 分類辞書の使い方、重複の防ぎ方、
銘柄ウォッチの決まりなど、手元の家計簿アプリから引き継いだものが書いてある。
支出・投資の作業をするときは必ずそちらも読む。

## 【最重要】読めないときは推測しない。ファイルを読む

**クラウド(サンドボックス)で動かすと、Supabase に届かない。**

Cowork のクラウド実行環境は、外に出られる宛先が決められている。
pypi や GitHub には出られるが、Supabase も Vercel も許可されていない。
宛先を足す設定は Team / Enterprise プランの組織設定にしかなく、
個人プランでは足せない。サンドボックス側から迂回もできない。
`j.context()` も `j.week()` も 403 で止まる。

### だから、フォルダのファイルを読む

パソコン側が、いまの在庫・献立・買い物リストを**ファイルに書き出している。**

```
C:\Users\mmizu\jisui\いまの状況.md
```

**献立の相談を受けたら、まずこれを読むこと。** あなたの
`device` のファイル読み取りの道具で読める(Supabase は要らない)。
中身は在庫(冷蔵・氷温・野菜・冷凍・常温の区画ごと)、これからの献立、
買い物リスト、好み・NG、直近に作ったもの、調理器具、常備品の在庫。

パソコンの見張りが**5分ごとに書き直している。**先頭に書き出した時刻がある。

### いま書き直させたいとき

本人がアプリで在庫や献立を直した直後だと、まだ古い中身のことがある。
**`更新して.txt` という名前の空ファイルを inbox に置くと、数秒で書き直される。**
置いたら5秒ほど待って、`いまの状況.md` を読み直すこと。
合図のファイルは見張りが消すので、後片付けは要らない。

先頭の時刻が本人の言う時刻より古いときは、これを使うこと。
古いまま答えて食い違うより、5秒待つほうがよい。

時刻がずっと古いままなら、パソコンが止まっている。そのときは
**古い時点の内容だと断ってから**答えること。黙って古い在庫で献立を組まない。

**「在庫が読めないので推測で提案します」と言わないこと。** 読める。
推測で組んだ献立は、買い物にも在庫にも合わず、丸ごと無駄になる。
実際にそう前置きして提案したことがある。

このファイルは**書き換えないこと。**次の書き出しで消える。
在庫を変えたいときは、いつもどおり `inbox` に受け渡し JSON を置く。

### 全部を直接やりたいなら、パソコン上で動かす

パソコン上で動けば 403 が無くなり、`j.context()` もそのまま通り、
書き込みも inbox を経由せず直接届く。切り替え方(日本語版の表記):

  ・タスクの **「…」(その他のオプション)** →
    **「お使いのコンピュータに移動」**
  ・または設定の **「このタスクの実行場所」** → **「このコンピューター」**

移すと **「このコンピューターで実行されます」** と出る。
**「プロジェクト」を付けたタスクは移せない**(アプリの表示:
「このコンピューターで実行されるセッションにはプロジェクトを
含めることができません」)。フォルダを付けること。

### つながらないときにやってはいけないこと

**代わりに手元の SQLite へ書かないこと。**
`jisui.db` と `kakeibo.db` はどちらも引退済みで、
`C:\Users\mmizu\jisui\_引退\自炊\_引退_2026-08-10\` に移してある。

書き込みは成功してしまうのに、アプリには何も出てこない。
だから「記録できた」と誤解したまま進んでしまう。
実際にそれで半日ぶんの記録がどこにも届かなかった。

**つながらないときは、SQLite に書く代わりに inbox へ JSON を置く。**次の節のとおり。

## つながらないときの受け渡し(inbox)

届かなくても、**話してもらった内容は捨てない。**
`db.py` は壁にぶつかると `JisuiOffline` を投げる。
この例外は【何を書けば復旧できるか】を丸ごと抱えている。

### 手順

```python
from db import Jisui, JisuiOffline

try:
    j = Jisui()
    j.add_receipt(date="2026-08-10", amount=1200,
                  merchant_raw="ライフ 西宮店", category="食費")
except JisuiOffline as e:
    h = e.handoff()      # → {"ファイル名": …, "中身": …, "件数": 1, "保存先": …}
    print(h["ファイル名"])
    print(h["中身"])
```

`h["中身"]`(JSON の文字列)を、`h["ファイル名"]` という名前で
**`h["保存先のフルパス"]` に保存する。**

### 書き方(Windows のパスをそのまま使う)

あなたの `remote-devices` の道具は、**`C:\…` のパスをそのまま受け取る。**
サンドボックスのファイルシステムには何も見えないが、それでよい。
道具ごしに書けば、パソコン側に本当に届く。

```
device_commit_files  →  C:\Users\mmizu\jisui\inbox\<h["ファイル名"]>
```

`/sessions/…` のような Linux のパスを組み立てないこと。**存在しない。**
(実測: `ls /sessions` → No such file or directory、`glob.glob("/sessions/*")` → `[]`)

`bash` はクラウドのコンテナで動いていて、そこからパソコンは見えない。
`ls` や `cat` でパソコンのファイルを確かめようとしても失敗する。
**確かめるのも道具(`device_list_dir`)でやること。**

### 【最重要】置いたら、必ず一覧して在ることを見てから報告する

```
1. device_commit_files で保存する
2. device_list_dir で C:\Users\mmizu\jisui\inbox を一覧する
3. そのファイルが在ることを目で見る
4. 見てから「置きました」と言う
```

**確かめる前に「置きました」と言わないこと。**

2026-08-11 に、置いていないのに「inbox に2件置いた」と報告した事故が起きている。
パソコン側のログを見ると、その時刻に書き込みを依頼した形跡が**1件も無かった**
(接続は生きていて、生存確認は34件出ていた)。記録は失われ、
本人は入ったものと思って先へ進んでいた。

**同じ理由で、一覧の結果も思い出しで答えないこと。** 同じ事故のあと、
「いま一覧したら3件あった」と報告されたが、実際にはその時刻に一覧した記録が無く、
数十分前の顔ぶれをそのまま述べていた。**毎回、必ず実行して、出た結果だけを言う。**

### 一覧に出てこなかったら

置けていない。**置けたと言わないこと。** そのまま本人に伝える。
`C:\Users\mmizu\jisui` がこのチャットにつながっているかを確かめてもらう。

**保存するのはあなた(エージェント)の仕事。** `db.py` はクラウドにいるので
パソコンのフォルダには書けないし、見えない。db.py は「何を書けばいいか」と
「どこに書くか」を返すところまでをやる。

保存できたら **必ず本人に伝える。**「つながらなかったので inbox に置いた。
パソコンの見張りが数秒で取り込む」と言う。黙って置くと、
入ったつもりでもう一度同じことを話してしまう。

### 場所と確かめ方を見る

```python
import db
db.inbox_status()
# → {"受け渡し場所": "C:\\Users\\mmizu\\jisui\\inbox", "確かめ方": [...], …}
```

### `Jisui()` を作る時点で落ちたとき

ログインの通信からして届かないので、**db.py には何をしようとしていたのか分からない。**
`e.handoff()` の `"中身"` は `None` になる。そのときは自分で組み立てる。
`handoff()` は**通信しない**ので、つながらなくても必ず動く。

```python
from db import handoff
h = handoff(
    ("add_receipt", {"date": "2026-08-10", "amount": 1200,
                     "merchant_raw": "ライフ 西宮店", "category": "食費"}),
    ("add_shopping", {"items": [{"item": "牛乳", "qty": "1本"}]}),
    note="8/10 の会話ぶん",
)
```

### JSON の形

1つのファイルに何件でも入る。1件でも同じ形にする(読む側が場合分けしなくて済む)。

```json
{
  "kind": "jisui-handoff",
  "version": 1,
  "created_at": "2026-08-10T08:24:43.668244+00:00",
  "skill_version": "2026-08-10.2",
  "note": "8/10 の会話ぶん",
  "records": [
    {
      "op": "add_receipt",
      "args": {
        "date": "2026-08-10",
        "amount": 1200,
        "merchant_raw": "ライフ 西宮店",
        "category": "食費",
        "source": "レシート",
        "items": null,
        "inventory": null,
        "needs_review": false,
        "memo": null
      },
      "key": "cfbfd8da01ec59b2fa267185f3316bab09fe5957b7714ebcfbb878bc9a64317d"
    }
  ]
}
```

| 場所 | 何のためにあるか |
|---|---|
| `kind` / `version` | 読む側が「これは受け渡し用だ」と分かるため。形を変えたら `version` を上げる |
| `created_at` | いつの会話ぶんか。順に適用したいときの手がかり |
| `skill_version` | どの版の db.py が書いたか。古い複製が動いていた事故があるので必ず残す |
| `op` | 何の操作か |
| `args` | 引数がそのまま。**`db.py` のメソッドの引数名と同じ**なので `j.add_receipt(**args)` と呼べる |
| `key` | 二重適用よけ。`sha256(op + "|" + args を並べ直した JSON)` |

**`key` には時刻を混ぜていない。** 混ぜると、同じ内容を2回書き出しただけで
別物になり、適用側が二重に入れてしまう。だから
**同じ操作からは必ず同じ `key`** が出る。適用したら `key` を控えておき、
すでにある `key` は飛ばす。それだけで何度流しても増えない。

ファイル名も内容だけで決まる(末尾8桁が全 `key` から作った印)。
同じ内容をもう一度書き出すと同じ名前になり、上書きになるのでファイルが増えない。

`args` に `household_id` は入れない。**入れるのは適用する側。**
そうしておくと、誰の資格情報で流しても正しい世帯に入る。

### 使える `op`

| `op` | `args` | 適用する側が呼ぶもの |
|---|---|---|
| `add_receipt` | `add_receipt` の引数そのまま | `j.add_receipt(**args)` |
| `add_shopping` | `{"items": [...]}` | `j.add_shopping(args["items"])` |
| `add_event` | `add_event` の引数そのまま | `j.add_event(**args)` |
| `add_todo` | `add_todo` の引数そのまま | `j.add_todo(**args)` |
| `add_rule` | `{"keyword", "category", "note"}` | `j.add_rule(**args)` |
| `insert` | `{"table": "…", "rows": [...]}` | `j.insert(args["table"], args["rows"])` |
| `update` | `{"table": "…", "match": {…}, "set": {…}}` | `j.update_rows(args["table"], args["match"], args["set"])` |
| `add_health` | `{"kind", "date", "member", …}` | `j.add_health(**args)` |
| `add_checkup` | `{"member", "date", "kind", "results": [...]}` | **アプリの受け渡し画面だけ**(下記) |
| `import_card_row` | `{date, amount, merchant_raw, merchant_norm, source, memo}` | 費目を `j.classify` で決めてから `transactions` へ |

### `add_health` — 体重・睡眠・歩数・飲酒を会話から記録する

**入力画面を開かない日をつくらないための入口。**
「今日7,000歩」「23時に寝て6時起き」「体重62.1」と言われたら、その場で受け渡しにする。

```json
{ "op": "add_health", "args": { "kind": "活動", "date": "2026-08-31", "member": "夫", "steps": 7000 } }
{ "op": "add_health", "args": { "kind": "睡眠", "date": "2026-08-31", "member": "妻",
                                "bedtime": "23:00", "wake_time": "06:00", "rest_feeling": 4 } }
{ "op": "add_health", "args": { "kind": "体重", "date": "2026-08-31", "member": "夫", "weight_kg": 62.1 } }
{ "op": "add_health", "args": { "kind": "飲酒", "date": "2026-08-31", "member": "夫", "pure_alcohol_g": 0 } }
```

| `kind` | 入れられる欄 |
|---|---|
| `体重` | `weight_kg` / `body_fat_pct` / `waist_cm` / `bp_systolic` / `bp_diastolic` / `memo` |
| `睡眠` | `bedtime` / `wake_time` / `rest_feeling`(1〜5) / `memo` |
| `活動` | `steps` / `active_minutes`(3メッツ以上) / `exercise_minutes` / `strength_training` / `memo` |
| `飲酒` | `pure_alcohol_g` / `drinks_memo` |

- `member` は **夫 / 妻** のどちらか。省けない
- `date` は**過ごした日**。睡眠は「23時に寝て6時起き」なら**起きた日**を渡す
- **同じ日の同じ人は上書き**になる。足し算ではない
- **`pure_alcohol_g: 0` は「休肝日」という記録。** 飲まなかった日は 0 を明示して入れること。
  行が無い日は「入れていない日」として扱われ、休肝日には数えられない
- 純アルコール量 = `量(ml) × 度数(%) × 0.8 / 100`
  (ビール500ml=20g / 日本酒1合=21.6g / ワイン150ml=14.4g / 焼酎水割り100ml=20g)
- **睡眠時間は送らない。** `hours` はデータベースが就寝と起床から計算する

**野菜量と塩分は `add_health` で入れない。** レシピの `veg_g` / `salt_g` から
献立ごとに自動で出る。レシピ側を `update` で埋めること。

```json
{ "op": "update", "args": { "table": "recipes", "match": { "name": "麻婆豆腐" },
                            "set": { "veg_g": 60, "salt_g": 2.4, "kcal": 380, "protein_g": 22 } } }
```

### `add_checkup` — 健康診断・人間ドック・血液検査の結果を残す

**紙で来た検査票を、そのまま記録に変える口。** 写真や PDF を読んで、
1回の受診を1件の受け渡しにする。アプリの**健康診断**の画面(`/health/exams`)に、
年ごとの推移として出る。

```json
{ "op": "add_checkup",
  "args": {
    "member": "夫", "date": "2026-06-09", "kind": "定期健診",
    "place": "◯◯クリニック", "overall": "A", "finding": "特記なし",
    "results": [
      { "item": "LDL-C", "value_num": 109, "unit": "mg/dl", "ref_low": 60, "ref_high": 119 },
      { "item": "γ-GTP", "value_num": 21, "unit": "IU/l", "ref_high": 50 },
      { "item": "尿蛋白", "value_text": "(−)", "ref_text": "(−)" }
    ]
  } }
```

| 欄 | 中身 |
|---|---|
| `member` | **夫 / 妻**。省けない |
| `date` / `kind` | 受けた日と種類(定期健診 / 人間ドック / 血液検査 / ABC検診 …)。この2つと `member` で同じ受診かを判定する |
| `overall` | 総合判定。**検査票の文字をそのまま**(A / B / C1 …)。良し悪しに読み替えない |
| `results[].value_num` | 数値。推移と前回比はこれだけを見る |
| `results[].value_text` | `(−)` や `異常なし` のように数値にならない結果 |
| `results[].ref_low` / `ref_high` / `ref_text` | **検査票に印刷されている基準を写す** |
| `results[].judge` | 項目ごとの判定(A / B / C …)。書いてあれば入れる |

- **基準を作らない。** 検査票に基準が書かれていない項目は、
  `ref_*` を空のままにする。アプリは「判定なし」と出す。
  一般的な基準を当てると、**手元の紙と画面で判定が食い違う**(同じ項目でも機関で基準が違う)
- **項目名の表記をそろえる。** 推移は名前で突き合わせるので、
  「γ-GTP」と「γ-GT」が混ざると別の項目として2行に割れる。
  `lib/checkup.ts` の `ITEM_ORDER` にある表記に合わせること
- **診断を書かない。**「◯◯の疑い」は `memo` にも入れない。値と基準だけを写す
- 同じ受診(同じ `member` / `date` / `kind`)は2回入らない。飛ばされる

**この `op` は inbox から流せない。** `scripts/apply-inbox.mjs` は知らない操作として
失敗する。**アプリの「チャットから取り込む」画面に JSON を貼る**こと
(検査票は本人の手元にあり、スマホで完結するほうが早い)。

### `update` — 既に入っている行を直す

**事実の訂正はこれで送る。** 使い切った食材を0にする、保管場所を直す、
献立を中止にする、レシピ本文を差し替える。以前は受け渡しに直す手段が無く、
すべて人がアプリで1件ずつ、あるいは SQL を手で流していた。

```json
{ "op": "update",
  "args": { "table": "inventory",
            "match": { "name": "小松菜", "location": "野菜" },
            "set":   { "qty": 0 } } }
```

| 決まりごと | なぜ |
|---|---|
| `match` が当たるのは**ちょうど1行のときだけ** | 0件でも2件以上でも【何もせずに失敗させる】。書く側は Supabase を読めないので、条件が何行に当たるかを知らないまま書いている。取り違えは黙って起きて、あとから原因が残らない |
| 直せる表は **`inventory` / `meal_plan` / `recipes` / `pantry` / `shopping_list` / `preferences`** だけ | 間違えたときに元の値が消える操作なので、家計簿の金額や世帯の設定は範囲に入れない |
| `set` に `id` と `household_id` は書けない | 別の行・別の世帯に化ける |
| **消す操作は無い** | 数量0と `status="中止"` で足りる。消すと受け渡しからは戻せない |
| `key` の作り方は他と同じ(`op` と `args` の sha256) | 同じ訂正を2回置いても1回しか通らない |

失敗すると `inbox` にファイルが残り、`ファイル名.json.error` に
「何行に当たったか」と当たった行が書かれる。`match` に列を足して絞り直す。

```json
{ "op": "update", "args": { "table": "meal_plan",
    "match": { "date": "2026-08-28", "slot": "夕食" },
    "set": { "status": "中止" } } }

{ "op": "update", "args": { "table": "recipes",
    "match": { "name": "麻婆豆腐" },
    "set": { "card_md": "# 麻婆豆腐\n\n## 基本情報\n…" } } }
```

`import_card_row` にだけ **費目が入っていない。**
費目を決めるには分類辞書を読む必要があり、それには接続が要るから。
**辞書を引くのは、つながる場所に着いてから。**
ここで AI が費目を推測して書き込むと、辞書と食い違って再現性が壊れる。

### 【繰り返す】inbox は SQLite の代わりではない

つながらないときの行き先は **inbox の JSON だけ**。
`jisui.db` にも `kakeibo.db` にも、新しく作った SQLite にも書かない。
SQLite は書き込みが成功してしまうので、**失敗したことに誰も気づけない。**
それで半日ぶんの記録が消えたように見えた事故が実際に起きている。
inbox の JSON は、置いたことが目に見えるし、あとから必ず適用できる。

## 【運用の前提】記録は必ず inbox に置く

**この家の使い方はこう決まっている。**

  ・チャット(あなた)はパソコンの Cowork から使う
  ・Supabase へは【届かない】。クラウドで動いていて、外向き通信が塞がれているため

  ・パソコンで常駐している見張りが、置かれた数秒後にアプリへ反映する

つまり **Supabase に直接書こうとして失敗するのを待つ必要は無い。**

そのほうが速いし、失敗のログで会話が汚れない。

置いたら、こう伝える:

> アプリを開き直すと出ています。

見張りが動いていない(パソコンを立ち上げた直後など)場合は、
次にログオンしたときにまとめて取り込まれる。**記録は失われない。**

## つながらないときの渡し方は2つある

Supabase に届かないとき、記録を捨てずに人へ渡す道が2本ある。
**相手がどこにいるかで選ぶ。**

### A. 会話にそのまま出す(スマホでも使える。こちらを既定にする)

受け渡し JSON を、コードブロックに入れて**会話にそのまま出す**。
利用者はそれをコピーして、アプリの **ホーム →「チャットから取り込む」** に貼る。
アプリはスマホからでも Supabase に届くので、**パソコンは一切要らない。**

    from db import handoff
    h = handoff(("add_receipt", {...}))
    print(h["中身"])        # ← これを会話に貼る

出したあとは、こう伝える:

> つながらなかったので、記録用の JSON を出しました。
> アプリの ホーム →「チャットから取り込む」に貼り付けてください。

### B. ファイルに置く(パソコンで作業しているとき)

接続済みフォルダの `inbox/` に JSON を保存する。
あとで `node scripts/apply-inbox.mjs --apply` が取り込む。
**デスクトップアプリが起きている必要がある**ので、スマホしか無いときは使えない。

**どちらの場合も、手元の SQLite には絶対に書かない。**
書き込みは成功してしまうのにアプリには何も出てこないため、
記録が消えたように見える。実際に半日ぶんそうなった。

## 接続情報の置き場所(つまずいたら最初にここを読む)

このスキルは2つの違う場所で動く。**動く場所によって、読める接続情報が違う。**

| 動く場所 | 読まれる設定 | 備考 |
|---|---|---|
| **Cowork(チャット)** | `cowork.json` | Anthropic のクラウドで動く。**このパソコンの中は一切見えない**。スキルとして保存したファイルだけが配られる |
| このパソコン | `.env`(無ければ `cowork.json`) | Claude Code や手元のスクリプト用。git 管理外 |
| どちらでも | 環境変数が最優先 | 秘密をファイルに置かずに済むならこれが一番よい |

**`cowork.json` はドットで始まらない名前にしてある。** `.env` のようなドットファイルは
zip にまとめるときに取りこぼされることがあり、それで一度つまずいた。

### 使うアカウント

チャットからは **Cowork 専用ユーザー**でログインする。夫のアカウントではない。理由:

- 接続情報はスキルに同梱するしかない = パスワードがスキルファイルに入る
- 専用ユーザーなら、漏れたときにそのユーザーのパスワードを変えるだけで無効化でき、
  人間2人のログインには影響しない

**このユーザーには非公開タグの予定は見えない。**持ち主本人だけが見える規則なので、
人間ではないこのユーザーには夫の分も妻の分も届かない。
「予定が1件足りない」と思っても壊れていない。

### 「接続情報が足りません」で止まったら

スキルに `cowork.json` が同梱されていない。保存し直すときに必ず入れること。
**そこで諦めて手元の jisui.db に書かないこと。**書けば “成功” してしまい、
記録がどこにも届かないまま消える。実際に一度そうなった。

## 守ること(これを外すと使えない提案になる)

1. **`好み・方針` の「苦手」は絶対に使わない。** 現在: トマト、バナナ
2. **`調理器具` にない器具を使うレシピは出さない。** 「オーブンで」と書いても家に無ければ意味がない

4. **レシピは初心者向けに「なぜ」まで解説する。** 「適量」「少々」は定義なしに使わない

5. **妻は少食だが増量方針。** 量ではなくカロリー密度で調整する(油・ナッツ・チーズを足す)
6. 完成したレシピは `recipes.card_md` に Markdown で入れる。アプリがそのまま表示する

### カード明細の CSV を取り込む

`jisui\inbox\` に置かれた CSV を `transactions` に入れる。
引退した家計簿スキルにあった機能で、**流儀もそのまま引き継いでいる。**

**Cowork(クラウド)からは `path=` が使えない。** db.py はクラウドのコンテナに
いるので、パソコンの CSV を自分では開けない。`path=` を渡すと、
どうすればよいかを書いた `JisuiError` が出る。手順はこう:

1. `device_read_file`(あなたのファイル読み取りの道具)で CSV の中身を読む
2. 読んだ中身を **`data=`** に渡して呼ぶ

```python
j.import_card_csv(data=<道具で読み取った中身>)
```

`path=` が使えるのは、**パソコン上で動いているとき**(「お使いのコンピュータに移動」でパソコンを
選んだとき、または Claude Code)だけ。文字コードと形は `data=` でも自分で見分ける。

読めるのは3つ。**実物を開いて列を確かめてある**(推測で足さないこと)。

| カード | ファイル名の例 | 文字コード | 見出し |
|---|---|---|---|
| 三井住友カード | `202608.csv` | Shift-JIS(cp932) | **無し**。1行目からいきなり明細 |
| 楽天カード | `enavi202608(2059).csv` | UTF-8(BOM付) | 有り |
| イオンカード | `meisai202608.csv` | Shift-JIS(cp932) | 前置きのあとに有り |

文字コードと形は `import_card_csv` が自分で見分ける。指定しなくてよい。

#### 必ず2回に分けて呼ぶ

```python
r = j.import_card_csv(r"C:\Users\mmizu\jisui\inbox\meisai202608.csv")
#   ↑ 1回目は【読むだけ】。dry_run=True が既定なので1行も書き込まない
```

`r["初見の店"]` を本人に見せて費目を決めてもらう。**承認されたぶんだけ**辞書に足す。

```python
j.add_rule("マックスバリュ", "食費")          # ← 人が「食費で」と言ってから
r = j.import_card_csv(path, dry_run=False)   # 2回目でようやく入る
j.archive_csv(path)                          # 報告してから processed/ へ移す
```

#### 守ること

1. **費目は辞書で決める。AI の判断で辞書と違う費目を付けない。**
   同じ店が月ごとに違う費目になると、月次の比較が意味を失う。再現性がこの機能の命
2. **初見の店を勝手に辞書へ登録しない。** 必ず本人に確かめてから `add_rule`
3. **口座番号・カード番号は保存しない。** イオンの明細は先頭に引落口座が書いてあるが、
   `db.py` は「ご利用明細」の行より前を**そもそも読まない**。8桁以上の数字も伏せる
4. `dry_run=False` にしても、初見の店が残っていれば **1行も書き込まずに止まる**。
   どうしても後回しにするなら `on_unknown="review"` で費目「要確認」・
   `needs_review=True` として入る(辞書には足さない)
5. **取り込んだら必ず報告する。** 取込件数・スキップ件数・費目別合計。
   `r` にそのまま入っている
6. **`archive_csv` は報告のあと。** 先に移すと、報告の途中で失敗したときに
   元の場所から消えていて何を取り込もうとしたのか分からなくなる

#### 報告の前に必ず見る2つ

- **`r["入らない行(鍵が同じ)"]` が 0 でないとき**
  `dedup_hash` は 日付・金額・店名 の3つだけで作る。だから同じ日に同じ店で
  同じ額を2回使うと、**本物の2件なのに1件しか入らない。**
  実際に起きている: `ＥＴＣ 中部地区 540円` が同じ日に2行(別の料金所)。
  `r["同じ鍵になってしまう行"]` に一覧が出るので、**黙って落とさず本人に見せる**
- **`r["スキップ(読めない行)"]`**
  日付や金額が読めなかった行。**推測で埋めない。**そのまま報告する

#### 口座明細は取り込まない

同じフォルダに銀行の明細(`RB-torihikimeisai.csv` / `ny*.csv` /
`nyushukinmeisai_*.csv`)も混ざっているが、**わざと扱わない。**
渡すと「これはカード明細ではありません」と言って止まる。理由は2つ:

- 口座明細にはカード代金の引落が入っている。カード明細と両方入れると
  **同じ買い物を2回数える**
- `ny*.csv` の日付は「6月5日」で年が無い。年を当てるのは推測になる

残高を記録したいなら `balances`、収入なら `income` に入れる。

#### つながらないとき

`import_card_csv` も `JisuiOffline` を投げる。例外は**明細1行ぶんずつ**
(`op` は `import_card_row`)を抱えているので、`e.handoff()` を inbox に保存する。

CSV はサンドボックスから見えない。**あなたが道具でファイルを読んで**中身を渡す。
`parse_card_csv` は通信しないので、つながらなくても動く。

**`open()` を使わないこと。** クラウドからパソコンのファイルは開けない。
記録をいちばん落としたくない場面で `FileNotFoundError` になる。

```python
from db import parse_card_csv, handoff
data = <あなたのファイル読み取りの道具で読んだ中身>
parsed = parse_card_csv(data, name="meisai202608.csv")
h = handoff(*[("import_card_row", row) for row in parsed["行"]],
            note="イオンカード 2026-08 明細")
# h["中身"] を h["ファイル名"] という名前で inbox に保存し、
# device_list_dir で在ることを確かめてから報告する
```

このとき**費目は付けない。**辞書が引けないので決めようがない。
決めるのは、つながる場所で適用するとき。

ctx = j.context()          # まずこれ

`location`(在庫の置き場所)は**5つだけ**。
**冷蔵 / 氷温 / 野菜 / 冷凍 / 常温**

うちの冷蔵庫(日立 R-HWC54Y)の引き出しに対応する。
肉・魚は**氷温**、葉物と根菜は**野菜**、玉ねぎ・いも類・未開封の調味料は**常温**。
切ってある野菜は**冷蔵**(氷温に入れてはいけない。凍って傷む)。
ここに無い言葉(「野菜室」「チルド」など)を書くと保存が弾かれる。

`section` は売り場順に使う。**野菜 / 肉・魚 / 乳製品・卵・豆腐 / 加工品・その他 / 調味料 / 冷凍 / 要確認 / セール枠**
のいずれか。安ければ買う候補は `セール枠` にする(アプリでは黄色の別枠になり、残り件数に入らない)。

### 予定を入れる・直す

`j.insert("events", ...)` の生 INSERT はもう使わない。`add_event` を通す
(持ち物や通知、非公開タグの面倒を見てくれる)。

| 言われたこと | 呼ぶもの |
|---|---|
| 「来週の火曜18時に歯医者、持ち物は保険証」 | `add_event(...)` |
| 「歯医者の予定いつだっけ」 | `find_events("歯医者")` |
| 「歯医者、来週にずらして」 | `move_event(id, "2026-08-19")` |
| 「場所を西宮北口に変えて」 | `update_event(id, location="西宮北口")` |
| 「あの予定消しといて」 | `delete_event(id)` → 中身を見せて → `confirm=True` |

```python
j.add_event(
    "2026-08-18", "歯医者", start_time="18:30", end_time="19:30",
    location="西宮北口 ◯◯歯科", url="https://…",
    items="保険証
診察券", notify_min=60,      # 60分前に通知
    tag="通院",
)
```

**「来週の火曜」は自分で日付に直してから渡す。** `add_event` は相対的な言い方を
解釈しない(今日が何日かを知っているのはこちら側なので)。今日の日付を確かめてから
`"2026-08-18"` の形にする。

```python
j.add_event("2026-08-15", "お盆で帰省", end_date="2026-08-17", all_day=True)  # 複数日・終日
j.add_event("2026-09-01", "資源ごみ", repeat="毎週", repeat_until="2027-03-31")  # 繰り返し
j.add_event("2026-08-20", "飲み会", start_time="19:00", mine=True)             # 自分だけの予定
```

- `all_day=True` で終日(時刻を空にする)。`end_date` で複数日
- `repeat` は **なし / 毎週 / 隔週 / 毎月 / 毎年**。行は1本だけ持ち、展開はアプリがやる。
  **消すと全部の回が消える。** 1回だけ動かしたいなら `move_event`
- `mine=True` で自分だけの予定。既定は2人の共有予定
- `move_event` は複数日の予定を長さごと平行移動する(`update_event` で `date` だけ
  変えると3泊が0泊になってしまう)

#### 非公開タグ — 見えないのが正しい

タグ(札)には「非公開」の設定がある。**非公開タグを付けた予定は、付けた本人にしか
見えない。相手の画面にはその予定が存在しない。**

```python
j.tags()      # [{"name": "通院", "private": False}, {"name": "内緒", "private": True}, …]
j.add_event("2026-08-22", "指輪を見に行く", tag="内緒")    # 「内緒」が非公開タグなら妻には見えない
```

- **妻が非公開で入れた予定は、ここからは1行も見えない。** これは不具合ではない。
  「予定が抜けている気がする」と言われても、探し回らないし、回避しようともしない
- 非公開タグは共有の予定には付けられない(付けると誰からも見えない行になるため、
  `add_event` がエラーで止める)
- タグを増やすのはアプリのタグ設定から。非公開かどうかもそこで決める

### 繰り返しのこと — 3つの置き場を使い分ける

同じ「毎週やること」でも、置き場が3つある。迷ったらこの表で決める。

| 種類 | 置き場 | 例 |
|---|---|---|
| 毎回同じ家事。チェックを付けて終わり | `chores` | ゴミ出し、風呂掃除、家賃の振込 |
| 時刻と場所のある予定 | `events` の `repeat` | 毎週火曜のジム、毎月の通院 |
| 期限のある宿題。1回ずつ内容が違う | `todos` の `repeat` | 月末の家計しめ、四半期の棚卸し |

```python
j.insert("chores", [{"name": "ゴミ出し(可燃)", "weekdays": [1, 4]}])   # 0=日〜6=土
j.insert("chores", [{"name": "家賃の振込", "weekdays": [], "monthday": 25}])
```

やった記録は `chore_log`。アプリのチェックと同じ場所に入る。

### やること(TODO)を作る・進める

| 言われたこと | 呼ぶもの |
|---|---|
| 「旅行準備のTODOを作って、宿予約と切符と保険を子タスクに」 | `add_todo(..., subtasks=[…])` |
| 「いま何が残ってる?」 | `todo_tree()` |
| 「宿の予約おわった」 | `done_todo(id)` |
| 「やっぱりまだだった」 | `reopen_todo(id)` |
| 「期限を来週末にして、担当は自分」 | `update_todo(id, due_date="…", assignee="自分")` |
| 「あのTODO消して」 | `delete_todo(id)` → 中身を見せて → `confirm=True` |

```python
j.add_todo(
    "旅行の準備", due_date="2026-09-01", assignee="自分",
    subtasks=["宿を予約する", "切符を取る", "旅行保険に入る"],
)
# → {"todo": {…親…}, "subtasks": [{…}, {…}, {…}]}
```

- **子タスクは `subtasks` に文字列を並べるだけで一度に作れる。** 1件ずつ入れなくてよい
- 子には期限も担当も付かない。親と違うことが多いので、必要なら後から `update_todo`
- 入れ子は**親→子の2階まで**(アプリの表示がその前提)。孫を作ろうとすると止まる
- **繰り返すやることの `done_todo(id)` は、行を消さずに期限を次回へ進める。**
  毎週のゴミ出しを完了にすると status は open のまま due_date が次の週になり、
  子タスクは未完了に戻る。「消えない」のは正しい動作。
  アプリの完了ボタンと同じ規則にしてある(片方だけ変えないこと)
- 繰り返さないやることの `done_todo(id)` は既定で**子タスクもまとめて完了**にする。子を残すなら
  `with_subtasks=False`
- `repeat` は **なし / 毎日 / 毎週 / 隔週 / 毎月 / 毎年**。次の回を出すのはアプリの仕事なので、
  ここで次の行を作らない(作ると二重に増える)
- 完了・未完了は `update_todo` では変えられない。`done_todo` / `reopen_todo` を使う
  (いつ・誰が終わらせたかを一緒に残すため)
- 本文の欄は `detail`。**`memo` と書いても同じ**ものとして受ける
  (`add_event` / `add_receipt` / `add_rule` が `memo` なので取り違えやすい)。
  両方渡したときは `detail` を採る

### 消す前に見せる

`delete_event` と `delete_todo` は、**そのままでは消さない。**
1回目の呼び出しは「何が消えるか」を返すだけ。

```python
j.delete_todo(12)                  # → {"消えるやること": {…}, "一緒に消える子タスク": [3件], "消した": False}
# 本人に見せて、いいと言われてから
j.delete_todo(12, confirm=True)    # → "消した": True
```

取り消しの仕組みは無い。**必ず中身を本人に見せてから消す。**
予定を消すとコメントも消え、繰り返しの予定は全部の回が消える。
終わったやることは、消さずに `done_todo` にしておくほうがよい(記録が残る)。

### 家計を見る・直す

```python
m = j.money("2026-08")
j.insert("transactions", [...])              # add_receipt を使うほうが安全(重複を弾く)
j.insert("budgets", [{"category": "食費", "amount": 45000, "year_month": None}])  # None=毎月

```

**資産・負債・給与は機密度が高い。** 設計書はもともとこれらをクラウドに置かない方針だった
(アプリで扱う判断に変更済み)。扱うときは次を守る。

- **口座番号・カード番号は絶対に保存しない**(列自体が無い)
- 残高や給与額を、依頼されていない相手や外部サービスへ渡さない
- 会話に残高を書くのは、本人が聞いたときだけにする

## 禁止事項

- **口座番号・カード番号は保存しない**(旧・家計簿スキルからそのまま踏襲。列自体を作っていない)
- **`kakeibo.db` と `jisui.db` には書き込まない。** どちらも引退済み。
  両方に書くと必ず食い違う
- **つながらないときに SQLite へ逃げない。**新しく作るのも駄目。
  行き先は `C:\Users\mmizu\jisui\inbox\` の JSON だけ(「つながらないときの受け渡し」)
- **費目を推測で付けない。**分類辞書(`expense_rules`)に無い店は「初見」として
  本人に確かめる。**承認なしに `add_rule` を呼ばない**
- **相手の非公開予定を回り込んで読もうとしない。** 見えないのは仕様。
  サービスキーを使う、RLS を外す、ビューを作る、といった抜け道を提案しない
  (ビューが RLS を素通りして家計データを漏らした事故が実際にある)
- **非公開タグの付いた予定を、要約や週次のまとめで相手に見せない。**
  そもそも取れないが、取れてしまったときも同じ
- 残高・給与・投資の額を、依頼されていない相手や外部サービスへ渡さない。
  会話に書くのは本人が聞いたときだけ
- レシート画像は非公開バケットに置き、署名付きURLでのみ読む
- 売買の推奨はしない。参考情報の整理までにとどめる
