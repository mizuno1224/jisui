# jisui(自炊と暮らしの管理)

## これは何か

夫婦2人の暮らしの記録。**同じデータをスマホアプリと共有している。**

| やること | どこでやるか |
|---|---|
| 買い物中のチェック、在庫の増減 | **アプリ**(片手で1タップ。オフラインでも動く) |
| 予定・家事のチェック | **アプリ**(カレンダーで見る) |
| レシート20点の一括登録 | **ここ**(写真1枚で金額込み全件が入る) |
| 献立の相談・レシピ生成 | **ここ**(会話で条件を足していける) |
| 好み・NG食材の登録 | **ここ**(会話の流れで自然に拾える) |
| 月次の振り返り | **ここ**(数字を並べて考える作業に向く) |

アプリで入れた在庫はここから見えるし、ここで入れたレシピはアプリに出る。

## まとめて読む3つの入口

用途ごとに、必要なものが一度で揃うようにしてある。手元の記憶で答えず、まずこれを呼ぶ。

```python
j.context()              # 献立を考える: 在庫・常備品・好み・器具・調理履歴・買い物リスト
j.week("2026-08-10")     # 予定を見る: その週の献立・予定・家事・家事の記録
j.money("2026-08")       # 家計を見る: その月の支出・収入・予算・資産と負債
j.investments()          # 投資を見る: 保有銘柄・監視銘柄・直近の指標・資産の内訳
j.outlook()              # 将来: ローン残高の予定・俸給表
j.find_events("歯医者")  # 予定を探す: 題名・メモ・場所・持ち物を横断で
j.todo_tree()            # やること: 親子の入れ子で
```

**お金の話の前に `C:\\Users\\mmizu\\家計簿\\方針.md` を読む。**
住宅ローンの条件、投資方針、そして「どの支出をどのカードで払うか」の
決めごとが書いてある。DB には入っていないので、読まないと毎回ずれた答えになる。

**家計簿の作法は KAKEIBO.md に分けてある。** 分類辞書の使い方、重複の防ぎ方、
銘柄ウォッチの決まりなど、手元の家計簿アプリから引き継いだものが書いてある。
支出・投資の作業をするときは必ずそちらも読む。

## 【最重要】このタスクはパソコン上で動かすこと

**クラウド(サンドボックス)で動かすと、Supabase に届かない。**

Cowork のクラウド実行環境は、外に出られる宛先が決められている。
pypi や GitHub には出られるが、Supabase も Vercel も許可されていない。
宛先を足す設定は Team / Enterprise プランの組織設定にしかなく、
個人プランでは足せない。サンドボックス側から迂回もできない。

### 直し方

新しいタスクを始めるとき、**右上の「Run this task」で実行場所を
【パソコン】にする。** それだけで制限が無くなり、そのまま届く。

### つながらないときにやってはいけないこと

**代わりに手元の SQLite へ書かないこと。**
`jisui.db` と `kakeibo.db` はどちらも引退済みで、
`C:\Users\mmizu\jisui\_引退_2026-08-10\` に移してある。

書き込みは成功してしまうのに、アプリには何も出てこない。
だから「記録できた」と誤解したまま進んでしまう。
実際にそれで半日ぶんの記録がどこにも届かなかった。

**つながらないときは、記録せずに「つながらなかった」と伝えるのが正解。**

## 接続情報の置き場所(つまずいたら最初にここを読む)

このスキルは2つの違う場所で動く。**動く場所によって、読める接続情報が違う。**

| 動く場所 | 読まれる設定 | 備考 |
|---|---|---|
| **Cowork(チャット)** | `cowork.json` | Anthropic のクラウドで動く。**このパソコンの中は一切見えない**。スキルとして保存したファイルだけが配られる |
| このパソコン | `.env`(無ければ `cowork.json`) | Claude Code や手元のスクリプト用。git 管理外 |
| どちらでも | 環境変数が最優先 | 秘密をファイルに置かずに済むならこれが一番よい |

**`cowork.json` はドットで始まらない名前にしてある。** `.env` のようなドットファイルは
zip にまとめるときに取りこぼされることがあり、それで一度つまずいた。

### 使うアカウント

チャットからは **Cowork 専用ユーザー**でログインする。夫のアカウントではない。理由:

- 接続情報はスキルに同梱するしかない = パスワードがスキルファイルに入る
- 専用ユーザーなら、漏れたときにそのユーザーのパスワードを変えるだけで無効化でき、
  人間2人のログインには影響しない

**このユーザーには非公開タグの予定は見えない。**持ち主本人だけが見える規則なので、
人間ではないこのユーザーには夫の分も妻の分も届かない。
「予定が1件足りない」と思っても壊れていない。

### 「接続情報が足りません」で止まったら

スキルに `cowork.json` が同梱されていない。保存し直すときに必ず入れること。
**そこで諦めて手元の jisui.db に書かないこと。**書けば “成功” してしまい、
記録がどこにも届かないまま消える。実際に一度そうなった。

## 使い方

すべて `db.py` を通す。SQLite の `jisui.db` はもう使わない(移行済み)。

```python
import sys; sys.path.insert(0, r"C:\Users\mmizu\.claude\skills\jisui")
from db import Jisui

j = Jisui()
ctx = j.context()   # 在庫・常備品・好み・器具・調理履歴・献立・買い物リスト
```

**献立やレシピの相談を受けたら、まず `j.context()` を呼ぶ。** 手元の記憶で答えない。
在庫は妻がアプリから動かしているかもしれない。

予定の 場所・URL・持ち物・通知・タグ と、TODO の 子タスク・繰り返し は
`schema_v5.sql` を Supabase で実行してから使える。まだのときは
「schema_v5.sql を実行してから使えます」というエラーが返る。

## 守ること(これを外すと使えない提案になる)

1. **`好み・方針` の「苦手」は絶対に使わない。** 現在: トマト、バナナ
2. **`調理器具` にない器具を使うレシピは出さない。** 「オーブンで」と書いても家に無ければ意味がない
3. **`常備品` にある調味料は買い物リストに載せない。米は絶対に載せない**(実家から貰うため)
4. **レシピは初心者向けに「なぜ」まで解説する。** 「適量」「少々」は定義なしに使わない
   - 例: 「なぜ火を止めて茹でる? 豚肉のたんぱく質は65℃を超えると急激に収縮して硬くなるため」
5. **妻は少食だが増量方針。** 量ではなくカロリー密度で調整する(油・ナッツ・チーズを足す)
6. 完成したレシピは `recipes.card_md` に Markdown で入れる。アプリがそのまま表示する

## よくある作業

### レシート写真から記録する

画像から店名・日付・合計・品目を読み取り、確認してもらってから:

```python
j.add_receipt(
    date="2026-08-09", amount=3070, merchant_raw="ライフ 西宮店",
    category="食費", source="レシート",
    items=[{"item": "豚ロース", "price": 680}, {"item": "なす", "price": 198}],
    inventory=[
        {"name": "豚ロース", "qty": 300, "unit": "g", "location": "冷蔵",
         "expiry": "2026-08-11", "bought_on": "2026-08-09", "price": 680},
        {"name": "なす", "qty": 2, "unit": "本", "location": "冷蔵", "bought_on": "2026-08-09"},
    ],
)
```

**1回の操作で支出と在庫の両方に入る。** 同じレシートを2回入れても `dedup_hash` で弾かれる。
カード明細でも同じ買い物が来そうなときは `needs_review=True` を付ける。

### 献立を提案する

```python
ctx = j.context()          # まずこれ
# 苦手を除き、器具の範囲で、在庫を使い切る向きに、直近2週間と被らないように考える
j.insert("meal_plan", [{"date": "2026-08-10", "slot": "夕食", "name": "…", "recipe_id": None}])
```

承認されたら、在庫に無いものだけ買い物リストへ:

```python
j.add_shopping([{"item": "鶏むね肉", "qty": "2枚", "reason": "8/10 唐揚げ", "section": "肉・魚"}])
```

`section` は売り場順に使う。**野菜 / 肉・魚 / 乳製品・卵・豆腐 / 加工品・その他 / 調味料 / 冷凍 / 要確認 / セール枠**
のいずれか。安ければ買う候補は `セール枠` にする(アプリでは黄色の別枠になり、残り件数に入らない)。

### レシピを登録する

```python
j.insert("recipes", [{
    "name": "…", "category": "主菜", "protein": "豚", "time_min": 15,
    "freezable": False, "card_md": "# …\n\n## 基本情報\n…",
}])
```

材料も入れる(アプリが在庫と突き合わせて「足りないものを買い物リストへ」を出すため):

```python
j.insert("recipe_ingredients", [{"recipe_id": 7, "name": "なす", "qty": 2, "unit": "本"}])
```

※ `recipe_ingredients` に `household_id` は無いので、`insert` ではなく直接入れる場合は注意。

### 在庫を直す

```python
j.update("inventory", {"qty": 1}, id="eq.12")
j.delete("inventory", id="eq.12")            # 使い切った
```

### 予定を入れる・直す

`j.insert("events", ...)` の生 INSERT はもう使わない。`add_event` を通す
(持ち物や通知、非公開タグの面倒を見てくれる)。

| 言われたこと | 呼ぶもの |
|---|---|
| 「来週の火曜18時に歯医者、持ち物は保険証」 | `add_event(...)` |
| 「歯医者の予定いつだっけ」 | `find_events("歯医者")` |
| 「歯医者、来週にずらして」 | `move_event(id, "2026-08-19")` |
| 「場所を西宮北口に変えて」 | `update_event(id, location="西宮北口")` |
| 「あの予定消しといて」 | `delete_event(id)` → 中身を見せて → `confirm=True` |

```python
j.add_event(
    "2026-08-18", "歯医者", start_time="18:30", end_time="19:30",
    location="西宮北口 ◯◯歯科", url="https://…",
    items="保険証
診察券", notify_min=60,      # 60分前に通知
    tag="通院",
)
```

**「来週の火曜」は自分で日付に直してから渡す。** `add_event` は相対的な言い方を
解釈しない(今日が何日かを知っているのはこちら側なので)。今日の日付を確かめてから
`"2026-08-18"` の形にする。

```python
j.add_event("2026-08-15", "お盆で帰省", end_date="2026-08-17", all_day=True)  # 複数日・終日
j.add_event("2026-09-01", "資源ごみ", repeat="毎週", repeat_until="2027-03-31")  # 繰り返し
j.add_event("2026-08-20", "飲み会", start_time="19:00", mine=True)             # 自分だけの予定
```

- `all_day=True` で終日(時刻を空にする)。`end_date` で複数日
- `repeat` は **なし / 毎週 / 隔週 / 毎月 / 毎年**。行は1本だけ持ち、展開はアプリがやる。
  **消すと全部の回が消える。** 1回だけ動かしたいなら `move_event`
- `mine=True` で自分だけの予定。既定は2人の共有予定
- `move_event` は複数日の予定を長さごと平行移動する(`update_event` で `date` だけ
  変えると3泊が0泊になってしまう)

#### 非公開タグ — 見えないのが正しい

タグ(札)には「非公開」の設定がある。**非公開タグを付けた予定は、付けた本人にしか
見えない。相手の画面にはその予定が存在しない。**

```python
j.tags()      # [{"name": "通院", "private": False}, {"name": "内緒", "private": True}, …]
j.add_event("2026-08-22", "指輪を見に行く", tag="内緒")    # 「内緒」が非公開タグなら妻には見えない
```

- **妻が非公開で入れた予定は、ここからは1行も見えない。** これは不具合ではない。
  「予定が抜けている気がする」と言われても、探し回らないし、回避しようともしない
- 非公開タグは共有の予定には付けられない(付けると誰からも見えない行になるため、
  `add_event` がエラーで止める)
- タグを増やすのはアプリのタグ設定から。非公開かどうかもそこで決める

### 繰り返しのこと — 3つの置き場を使い分ける

同じ「毎週やること」でも、置き場が3つある。迷ったらこの表で決める。

| 種類 | 置き場 | 例 |
|---|---|---|
| 毎回同じ家事。チェックを付けて終わり | `chores` | ゴミ出し、風呂掃除、家賃の振込 |
| 時刻と場所のある予定 | `events` の `repeat` | 毎週火曜のジム、毎月の通院 |
| 期限のある宿題。1回ずつ内容が違う | `todos` の `repeat` | 月末の家計しめ、四半期の棚卸し |

```python
j.insert("chores", [{"name": "ゴミ出し(可燃)", "weekdays": [1, 4]}])   # 0=日〜6=土
j.insert("chores", [{"name": "家賃の振込", "weekdays": [], "monthday": 25}])
```

やった記録は `chore_log`。アプリのチェックと同じ場所に入る。

### やること(TODO)を作る・進める

| 言われたこと | 呼ぶもの |
|---|---|
| 「旅行準備のTODOを作って、宿予約と切符と保険を子タスクに」 | `add_todo(..., subtasks=[…])` |
| 「いま何が残ってる?」 | `todo_tree()` |
| 「宿の予約おわった」 | `done_todo(id)` |
| 「やっぱりまだだった」 | `reopen_todo(id)` |
| 「期限を来週末にして、担当は自分」 | `update_todo(id, due_date="…", assignee="自分")` |
| 「あのTODO消して」 | `delete_todo(id)` → 中身を見せて → `confirm=True` |

```python
j.add_todo(
    "旅行の準備", due_date="2026-09-01", assignee="自分",
    subtasks=["宿を予約する", "切符を取る", "旅行保険に入る"],
)
# → {"todo": {…親…}, "subtasks": [{…}, {…}, {…}]}
```

- **子タスクは `subtasks` に文字列を並べるだけで一度に作れる。** 1件ずつ入れなくてよい
- 子には期限も担当も付かない。親と違うことが多いので、必要なら後から `update_todo`
- 入れ子は**親→子の2階まで**(アプリの表示がその前提)。孫を作ろうとすると止まる
- **繰り返すやることの `done_todo(id)` は、行を消さずに期限を次回へ進める。**
  毎週のゴミ出しを完了にすると status は open のまま due_date が次の週になり、
  子タスクは未完了に戻る。「消えない」のは正しい動作。
  アプリの完了ボタンと同じ規則にしてある(片方だけ変えないこと)
- 繰り返さないやることの `done_todo(id)` は既定で**子タスクもまとめて完了**にする。子を残すなら
  `with_subtasks=False`
- `repeat` は **なし / 毎日 / 毎週 / 隔週 / 毎月 / 毎年**。次の回を出すのはアプリの仕事なので、
  ここで次の行を作らない(作ると二重に増える)
- 完了・未完了は `update_todo` では変えられない。`done_todo` / `reopen_todo` を使う
  (いつ・誰が終わらせたかを一緒に残すため)

### 消す前に見せる

`delete_event` と `delete_todo` は、**そのままでは消さない。**
1回目の呼び出しは「何が消えるか」を返すだけ。

```python
j.delete_todo(12)                  # → {"消えるやること": {…}, "一緒に消える子タスク": [3件], "消した": False}
# 本人に見せて、いいと言われてから
j.delete_todo(12, confirm=True)    # → "消した": True
```

取り消しの仕組みは無い。**必ず中身を本人に見せてから消す。**
予定を消すとコメントも消え、繰り返しの予定は全部の回が消える。
終わったやることは、消さずに `done_todo` にしておくほうがよい(記録が残る)。

### 家計を見る・直す

```python
m = j.money("2026-08")
j.insert("transactions", [...])              # add_receipt を使うほうが安全(重複を弾く)
j.insert("budgets", [{"category": "食費", "amount": 45000, "year_month": None}])  # None=毎月
j.insert("income",  [{"date": "2026-08-25", "amount": 300000, "source": "給与(夫)"}])
j.insert("accounts",[{"name": "三井住友銀行", "kind": "資産", "category": "預金"}])
j.insert("balances",[{"account_id": 1, "year_month": "2026-08", "amount": 1200000}])
```

**資産・負債・給与は機密度が高い。** 設計書はもともとこれらをクラウドに置かない方針だった
(アプリで扱う判断に変更済み)。扱うときは次を守る。

- **口座番号・カード番号は絶対に保存しない**(列自体が無い)
- 残高や給与額を、依頼されていない相手や外部サービスへ渡さない
- 会話に残高を書くのは、本人が聞いたときだけにする

## 禁止事項

- **口座番号・カード番号は保存しない**(旧・家計簿スキルからそのまま踏襲。列自体を作っていない)
- **`kakeibo.db` と `jisui.db` には書き込まない。** どちらも引退済み。
  両方に書くと必ず食い違う
- **相手の非公開予定を回り込んで読もうとしない。** 見えないのは仕様。
  サービスキーを使う、RLS を外す、ビューを作る、といった抜け道を提案しない
  (ビューが RLS を素通りして家計データを漏らした事故が実際にある)
- **非公開タグの付いた予定を、要約や週次のまとめで相手に見せない。**
  そもそも取れないが、取れてしまったときも同じ
- 残高・給与・投資の額を、依頼されていない相手や外部サービスへ渡さない。
  会話に書くのは本人が聞いたときだけ
- レシート画像は非公開バケットに置き、署名付きURLでのみ読む
- 売買の推奨はしない。参考情報の整理までにとどめる
