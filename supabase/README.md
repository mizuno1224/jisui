# SQL の置き場所

Supabase の SQL Editor に貼って実行するファイル。**番号の順に流す。**

もとはリポジトリの一番上に12本ばらばらに置いてあり、
「どれをどの順で流すのか」が名前から読めなかった。実際に何度も迷ったので、
名前の先頭に番号を付けた。

## 13 以降(あとから足したもの)

| 番号 | ファイル | 何をするか | 何度流してよいか |
|---|---|---|---|
| 13 | `13_cook_log_marks_plan.sql` | 作った記録が入ったら、その日の献立を「実施」にする | **よい**(作り直すだけ) |
| 13b | `13b_backfill_once.sql` | すでに溜まっているぶんの状態を揃える | **一度きり**(人が戻した行まで実施に戻る) |
| 14 | `14_share.sql` | 支出を 夫婦/夫/妻 に振り分ける | よい |
| 15 | `15_dup_check.sql` | 二重計上の疑いを見つける | よい |
| 16 | `16_payer.sql` | 誰が払ったかを持つ | よい |
| 18 | `18_check_cook_plan.sql` | **13 が本当に入っているかを見る(何も書き換えない)** | よい |
| 19 | `19_health.sql` | 健康(体重・睡眠・活動・飲酒・検診・予防接種・目標値)とレシピの栄養 | よい |

**流したかどうかは、ファイルがあることでは分からない。**
2026-08-27、作った記録を入れても献立が「予定」のままになった。
2026-08-30 に本番を確かめたところ、13 の**関数は入っていた**(判定も正しい)。
残る疑いはトリガが表に付いているかで、それは SQL Editor でしか見えない。

流していなくても、トリガだけ外れていても、**何も起きないだけでエラーは出ない。**
だから「直したつもりで直っていない」に気づく道を別に用意してある。

**献立の状態がおかしいと思ったら、まず `18_check_cook_plan.sql` を流す。**
全部 select なので、いつ流しても安全。①〜⑤の見方はファイルの中に書いてある。

### 19 を流すときの順番

`19_health.sql` は**アプリより先に流してよい**(12a/12b のような順序の縛りは無い)。
表が無いあいだ、健康タブは「19_health.sql を実行してください」と出すだけで、
ほかの画面は何も壊れない。Cowork が読む いまの状況.md も止まらない
(`db.py` の `health()` が、表が無いときは「まだ始めていない」と返す)。

生年月日・身長・その日の体重は `preferences` の「体格」の行から写す。
**空の欄にしか入れない**ので、アプリで直したあとに流し直しても踏まない。

---

**06 を飛ばさないこと。** 素の `04_schema_kakeibo.sql` が作るビューは
PostgreSQL の既定で「作成者の権限」で動くため、**ログインしていない相手にも
家計データを返してしまう**。公開鍵は誰でも読めるので実害がある。

## tests/ — 実測で確かめる

| ファイル | 何を確かめるか |
|---|---|
| `tests/private_events.sql` | **非公開の予定が本当に相手から見えないか**(11項目) |

`11_schema_v5.sql` を流したあと、必ず1回これを実行する。
「ポリシーを書いた」と「隠せている」は別物で、過去にビュー経由で
家計データが匿名に漏れていた事故がある。設定画面が緑でも意味がない。

予定まわりを触ったときも、そのつど流し直すこと。

## 書くときの決まり

- **何度流しても壊れないこと。**本番に実データが入っている。
  `create table if not exists` / `add column if not exists` /
  `drop policy if exists` → `create policy` / `on conflict do nothing`
- **末尾に確認用の SELECT を置く。**「結果」と「期待」を並べ、
  全部一致すれば成功と分かる形にする
- **ビューを作るときは必ず `security_invoker = on`。**
  既定のビューは作成者権限で動き、RLS を素通りする
- **日本語のコメントで「なぜそうするか」を書く。**半年後に読む人が前提を知らない
