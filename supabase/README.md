# SQL の置き場所

Supabase の SQL Editor に貼って実行するファイル。**番号の順に流す。**

もとはリポジトリの一番上に12本ばらばらに置いてあり、
「どれをどの順で流すのか」が名前から読めなかった。実際に何度も迷ったので、
名前の先頭に番号を付けた。

---

## 新しく作り直すとき(番号順に1回ずつ)

| 番号 | ファイル | 何をするか |
|---|---|---|
| 01 | `01_schema.sql` | 表と RLS の土台 |
| 02 | `02_seed.sql` | 最初のデータ(器具・常備品・在庫・レシピ・買い物リスト) |
| 03 | `03_patch_members.sql` | 相手の名前が見えるようにする |
| 04 | `04_schema_kakeibo.sql` | 家計簿の表 |
| 05 | `05_seed_kakeibo.sql` | 取引155件・分類辞書67件 |
| 06 | **`06_patch_views_rls.sql`** | **必須。**ビューが RLS を素通りする穴をふさぐ |
| 07 | `07_schema_v2.sql` | 予定・家事・予算・資産・収入 |
| 08 | `08_schema_v3.sql` | 予定のラベル・繰り返し・やりとり |
| 09 | `09_schema_v4.sql` | 資産の内訳・保有銘柄・俸給表・ローン予定・やること |
| 10 | `10_seed_v4.sql` | 家計簿アプリから移したデータ |
| 11 | `11_schema_v5.sql` | 予定のタグと**非公開の予定**・やることの親子と繰り返し |
| 12 | `12_schema_v6.sql` | 冷蔵庫の区画を実機に合わせる |

**06 を飛ばさないこと。** 素の `04_schema_kakeibo.sql` が作るビューは
PostgreSQL の既定で「作成者の権限」で動くため、**ログインしていない相手にも
家計データを返してしまう**。公開鍵は誰でも読めるので実害がある。

## tests/ — 実測で確かめる

| ファイル | 何を確かめるか |
|---|---|
| `tests/private_events.sql` | **非公開の予定が本当に相手から見えないか**(11項目) |

`11_schema_v5.sql` を流したあと、必ず1回これを実行する。
「ポリシーを書いた」と「隠せている」は別物で、過去にビュー経由で
家計データが匿名に漏れていた事故がある。設定画面が緑でも意味がない。

予定まわりを触ったときも、そのつど流し直すこと。

---

## 書くときの決まり

- **何度流しても壊れないこと。**本番に実データが入っている。
  `create table if not exists` / `add column if not exists` /
  `drop policy if exists` → `create policy` / `on conflict do nothing`
- **末尾に確認用の SELECT を置く。**「結果」と「期待」を並べ、
  全部一致すれば成功と分かる形にする
- **ビューを作るときは必ず `security_invoker = on`。**
  既定のビューは作成者権限で動き、RLS を素通りする
- **日本語のコメントで「なぜそうするか」を書く。**半年後に読む人が前提を知らない
