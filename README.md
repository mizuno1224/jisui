# くらし(リポジトリ名は jisui)

夫婦2人の暮らしを1つにまとめた PWA。スマホのホーム画面から使う。

| 読みたいこと | どこ |
|---|---|
| **使い方**(操作方法) | **アプリの中**。買い物タブ「⋮」→「使い方」(本文は [lib/help-content.ts](lib/help-content.ts)) |
| **しくみ**(なぜこう作ったか・どこが壊れやすいか) | [しくみ.md](docs/しくみ.md) |
| **環境の作り方**(Supabase / Vercel) | [セットアップ手順.md](docs/セットアップ手順.md) |
| **何を作るつもりだったか** | [設計書.md](docs/設計書.md) |
| この下 | 開発者向けの手順と注意点 |

| タブ | できること |
|---|---|
| **買い物** | 売り場順・行全体タップ・残り件数・セール枠は別枠。**オフラインでも動く** |
| **在庫** | 冷蔵/冷凍/常温・+/- で増減・期限警告・使う予定の献立を併記 |
| **レシピ** | カード表示(なぜまで解説)・材料と在庫の突き合わせ・足りない分を買い物リストへ |
| **献立** | 予定と実績・作った記録・調理履歴 |
| **家計** | 今月の費目別・**1食あたりコスト**・重複確認が必要な行 |

### AI機能はアプリに入れていない

レシート読み取り・献立提案・レシピ生成は **Cowork(チャット)側**で行う(設計書 3-4)。
アプリに Claude API キーを持たせると別料金になるが、チャットは購読の範囲で動くため。
チャットから同じ Supabase を読み書きする道具は `cowork/jisui/` にある。

| やること | どこで | なぜ |
|---|---|---|
| 買い物中のチェック、在庫の増減 | アプリ | 片手で1タップ。オフラインでも動く |
| レシート20点の一括登録 | チャット | 写真1枚で金額込み全件が入る |
| 献立の相談・レシピ生成 | チャット | 会話で条件を足していける |

### チャットが Supabase に届かないときは inbox に置く

Cowork はクラウドで動いていて、外に出られる宛先が決まっている。
**Supabase はその中に入っていない**(実測で確定。中継を Vercel に置いても、
Vercel 自体が同じ壁なので成立しない)。何もしないと、話した内容がその場で消える。
一度これで、記録が SQLite に入って “成功” してしまい、
アプリにはどこにも出てこない、という事故を起こしている。

そこで `cowork/jisui/db.py` は、届かなかったときに例外で終わらせず
「何を書けば復旧できるか」を JSON にして返す。チャットはそれを
`C:\Users\mmizu\jisui\inbox\` に置く(そこだけはチャットから書けるため)。
**記録を失わないための受け渡し**で、置いたことは目に見える。

その JSON を、つながるこのパソコンで流し込むのが `scripts/apply-inbox.mjs`。

```bash
node scripts/apply-inbox.mjs           # 下見。何を入れるつもりかを1件ずつ出すだけ。何も書かない
node scripts/apply-inbox.mjs --apply   # 実際に入れて、済んだファイルを processed/ へ移す
```

書き込みは db.py 自身にやらせる(接続情報も入れ方も二重に持たないため)。
**何度実行しても増えない。** 済んだファイルは `processed/` へ移し、適用した
record の鍵を `jisui\applied-keys.json` に控えて次からは飛ばす。
**この控えは消さないこと**(買い物・予定・やることは DB 側に重複よけが無く、
守っているのはこの控えだけ。レシートとカード明細は `dedup_hash` でも守られる)。

受け渡し場所は 2026-08-11 に `家計簿\inbox` から `jisui\inbox` へ移した。
`scripts/watch-inbox.mjs` は**古いほうも見張り続ける**。Cowork の接続先を
変え忘れたときに、記録が誰も見ていない場所に置かれるのを防ぐため。
どちらから取り込んでも、控えと `processed/` は `jisui\` のものを使う
(控えが 2 つに分かれると同じ記録が二重に入る)。

1件失敗しても残りは続ける。失敗したファイルは inbox に残り、理由が
`<名前>.json.error` に書かれる。直してもう一度 `--apply` すれば、
入ったぶんを飛ばして続きからやり直す。

## 1. すぐ動かす(Supabaseなし)

```bash
npm install
npm run dev
```

http://localhost:3000 を開く。環境変数が無いときは **ローカルモード** になり、
02_seed.sql と同じ6件をこの端末の中だけで扱う。画面の作りを試すのはこれで足りる。

## 2. Supabase につなぐ

### 2-1. SQL を実行する

Supabase の SQL Editor に、この順で貼って実行する。

| 順 | ファイル | 中身 |
|---|---|---|
| 1 | `01_schema.sql` | テーブル・RLS・リアルタイム設定 |
| 2 | `02_seed.sql` | 既存データ(器具11・常備品32・在庫18・レシピ6 ほか) |
| 3 | `03_patch_members.sql` | 相手の表示名が読めるようにする(任意。下記) |
| 4 | `04_schema_kakeibo.sql` | 家計簿(支出)のテーブル。使うのはフェーズ3 |
| 5 | `05_seed_kakeibo.sql` | 取引155件・分類辞書67件 |

`03_patch_members.sql` は任意。素の `01_schema.sql` では `household_members` の
SELECT ポリシーが自分の行しか返さないため、「誰がチェックしたか」の欄が
相手のときに `パートナー` の固定表示になる。実名を出したい場合だけ当てる。

### 2-2. ユーザーを2人作って世帯に入れる

Authentication → Users で2人分を作る(または一度ログインして自動作成させる)。
そのうえで SQL Editor から:

```sql
insert into household_members (household_id, user_id, display_name) values
  ('00000000-0000-4000-8000-000000000001', '<夫のuser_id>', '夫'),
  ('00000000-0000-4000-8000-000000000001', '<妻のuser_id>', '妻');
```

世帯 id は `02_seed.sql` が作る固定値。**ここを入れないと RLS で1件も見えない。**

### 2-3. ログイン方式(パスワード)

**メールアドレス + パスワード**でログインする。Redirect URLs の登録は不要。
手順2-2 でユーザーを作るときに決めたパスワードをそのまま使う。

設計書ではマジックリンクを想定していたが、2点の理由でパスワードに変えた。

- **iOS のホーム画面アプリは Safari と保管庫が分かれている。** メールのリンクは Safari で開くため、
  ログイン状態がホーム画面アプリに入らず、いつまでもログインできない
- **Supabase の標準メールはチームメンバー宛のみ・1時間2通。** 妻のアドレスに届かない

パスワードを忘れたときは Authentication → Users から再設定する。

### 2-4. 環境変数

```bash
cp .env.local.example .env.local
# NEXT_PUBLIC_SUPABASE_URL と NEXT_PUBLIC_SUPABASE_ANON_KEY を埋める
```

anon key は公開前提。守りは RLS で行う(設計書 7)。

## 3. Vercel へ出す

```bash
git init && git add -A && git commit -m "jisui phase 1"
# GitHub に push → Vercel で Import
```

Vercel の Environment Variables に上の2つを登録する。`jisui.db` や生成HTMLは
一つ上の `jisui\` にあるので、リポジトリには入らない。

## 4. スマホのホーム画面に追加

本番URLを開いて「ホーム画面に追加」。iOS は Safari から行う必要がある。
追加後はアドレスバーなしの全画面で立ち上がる。

## オフラインの確かめ方

Service Worker は本番ビルドのときだけ登録される(開発中は HMR とぶつかるため)。

```bash
npm run build && npm start
```

DevTools → Application → Service Workers で Offline にチェック → リロード。
アプリが起動し、チェックが効き、ヘッダーに「オフライン」「未送信 n」が出れば正しい。
オンラインに戻すと自動で送信され、バッジが消える。

## 画面を変えて本番へ出すとき

`public/sw.js` の `VERSION` を1つ上げてから push する。

Service Worker はアプリ本体をキャッシュしているが、`sw.js` の中身が変わらないと
ブラウザは「同じもの」と判断して入れ替えない。オンラインなら新しい HTML を取りに行くので
気づきにくいが、**圏外で起動したときだけ古い画面が出る**。

## 触るときに壊しやすい所

実際に壊れていて直した箇所。同じ形で戻りやすいので残しておく。

**認証の確認を待ってから画面を出さない。** `init()` は手元(IndexedDB)を読んだ
時点で `status: "ready"` にする。`getSession()` は期限切れだと更新のため通信に出るので、
圏外だと数十秒止まる。待つと、店内で買い物リストが1件も見えない時間ができる。

**「ログインが切れた」と判断してよいのは、オンラインで401を返されたときだけ。**
タイムアウトや `session === null` は「確認できなかった」であって「切れた」ではない。
`navigator.onLine` はリロード後に true へ戻るため判断材料にならない。

**操作を積む条件は `signedIn` ではなく `householdId`。** 圏外で認証が確認できない
場面こそ、タップを outbox に残す必要がある。

**postgrest-js は通信失敗・中断でも error を返す。** その中身は `code: ""` /
`status: 0`。「code が文字列なら拒否」と見ると、弱電波でタイムアウトした操作を
サーバ拒否と誤判定して捨ててしまう(`isPermanent()` を使う)。

**`key={tick}` で再描画しようとしない。** `useTable` の state は画面コンポーネント側に
あるので、`<main key>` を変えても再取得されない。`refetch()` を呼ぶ。

**書き込み後にキャッシュを空配列で上書きしない。** 直後に圏外になると「データが無い」
と表示される。`markStale()` で印を立てるだけにする。

**`backdrop-blur` の中に `fixed inset-0` を置かない。** ぼかしは fixed の基準に
なるため、その要素の高さぶんしか広がらない。メニューを閉じる面が画面下を覆えず、
背後の商品行が反応していた。

**表記ゆれは正規化だけでは吸収できない。** 全角/カタカナ/大小は機械的に寄せられるが、
「玉ねぎ」と「たまねぎ」は読みの辞書が要る。`lib/matching.ts` の対応表に
よく使うものだけ手で並べてある。網羅はしない(外れても別の行として足されるだけ)。

**繰り返し予定は実体化しない。** サーバには1行だけ持ち、表示のたびに
`occursOn()` で日付に当てて広げる。何十行も作ると、消すときに取りこぼし、
直したときに過去ぶんだけ古いまま残る。

## 決めごと(実装の理由)

**チェックは待たない。** タップした瞬間に IndexedDB へ書いて画面を更新し、
送信用の操作を outbox に積む。オンラインになった時点で積んだ順に流す
(`lib/store.ts`)。スーパーの地下で電波が切れても、操作は消えない。

**競合は「チェック済みが勝つ」。** 二重購入を防ぐのが最優先なので、
チェックは無条件で通す。逆に、チェックを外す操作は「自分がタップした後に
相手がチェックしていたら通さない」(`.lte("checked_at", op.at)`)。
外したいときはもう一度タップすればよい。

**セール枠は残り件数に含めない。** 「安ければ買う」候補であって、
買えなくても買い物は終わるため。黄色の別セクションで最後に出す。

**行全体がタップ領域(高さ64px)。** 片手で、あまり見ずに押せることを優先した。
もう一度タップで戻せる。長押しで削除。

```

lib/local-db.ts         IndexedDB(items / inventory / outbox / cache / meta)
```

**`cowork/jisui/` が正本です。**`~/.claude/skills/jisui/` は
`scripts/sync-skill.ps1` で配った写し。片方だけ直すと、古いほうが動き続けます。
一度これで半日ぶんの記録がどこにも届かない事故を起こしています。

## SQL の実行順

**[supabase/README.md](supabase/README.md) に移しました。**番号順に流します。

`06_patch_views_rls.sql` は必ず当てること。素の `04_schema_kakeibo.sql` が作る
ビューは PostgreSQL の既定で「作成者の権限」で動くため、**ログインしていない
相手にも家計データを返してしまう**。公開鍵は誰でも読めるので実害がある。

`11_schema_v5.sql` を流したあとは `supabase/tests/private_events.sql` を実行して、
非公開の予定が本当に隠れているかを実測すること。
