# Claude Code への報告: アプリと Cowork がまだ連携していない

2026-08-09 の Cowork セッションで判明したことの報告です。
`cowork/jisui/` の橋は架かっているのに、実際には渡れていない状態でした。

---

## 1. 何が起きたか

**Cowork(チャット)側は、8/9 時点でもまだ引退済みの `jisui.db` に書き込み続けていました。**

Cowork のアカウントに保存されている jisui スキルが **8/5 版のまま**です。説明文が
「データは jisui.db(SQLite)に蓄積する」となっており、`app/cowork/jisui/SKILL.md`
(8/8 作成・Supabase 版)に置き換わっていません。

そのため 8/9 の会話でユーザーが行った記録は、すべて `C:\Users\mmizu\jisui\jisui.db`
に入っており、**Supabase には 1 件も届いていません**。ユーザーは「アプリに反映
されているはず」と考えていたので、認識と実態がずれていました。

---

## 2. つながっていない原因は 2 つ

### 原因 A: 新しいスキルが Cowork アカウントに保存されていない

`app/cowork/jisui/` に SKILL.md(175行)・KAKEIBO.md(122行)・db.py(370行)が
揃っており、中身は完成しています。しかしこれは **リポジトリ内にファイルとして
存在するだけ**で、Cowork のスキルとしては登録されていません。

Cowork のセッションは `~/.claude/skills/jisui/SKILL.md` を読みます。ここが 8/5 版の
ままなので、いくらリポジトリを更新しても Cowork の挙動は変わりません。
**スキルの保存はユーザーが Claude アカウント上で行う必要があり、Claude Code からも
Cowork からも自動ではできません。**

### 原因 B: `.env` が未作成

`app/cowork/jisui/.env.example` はありますが `.env` がありません。`db.py` の
`_load_config()` は `.env` か環境変数から次の 4 つを読みますが、どちらも空のため
`JisuiError` で止まります。

```
JISUI_SUPABASE_URL
JISUI_SUPABASE_KEY
JISUI_EMAIL
JISUI_PASSWORD
```

---

## 3. 設計上、いま決める必要があること(重要)

`db.py` の `_load_config()` は `.env` を **`db.py` と同じディレクトリ**から読みます
(`Path(__file__).with_name(".env")`)。

ここで問題になるのが、**Cowork のスキルはユーザーのパソコンではなく Anthropic の
クラウドサンドボックスで動く**という点です。スキルとして保存された SKILL.md と
db.py はサンドボックスに配られますが、`.env` は git 管理外なので配られません。

つまり `.env` をリポジトリに置いたままだと、Cowork は毎回デスクトップアプリ経由で
`.env` を取りに行くことになり、**「パソコンを開いていないと動かない」という、
今回の移行で解消したかった問題がそのまま残ります。**

`_load_config()` は環境変数へのフォールバックを実装済みなので、次のどれかを選んで
SKILL.md に明記してほしいです。

| 案 | やり方 | 評価 |
|---|---|---|
| **A. スキルに `.env` を同梱** | スキルの zip に `.env` を入れて保存する | パソコン不要になる。ただし**パスワードがスキルファイルに入る**ため、扱いに注意が必要 |
| **B. 専用ユーザーを作る** | Supabase Auth に Cowork 専用ユーザーを作り、その認証情報だけを A の方式で同梱 | 漏れても影響が限定される。**推奨** |
| C. 毎回デスクトップから読む | 現状のまま | パソコン依存が残る。移行の目的を果たせない |

**B を推奨します。** 世帯には参加させるが、人間のログインとは別アカウントにして
おけば、後から revoke もできます。

## 5. アプリ側に反映してほしい仕様(冷蔵庫)

ユーザーの冷蔵庫が **日立 R-HWC54Y(2026年製・540L・6ドア)** と判明しました。
「まるごとチルド」搭載機で、保管場所の考え方が一般的な冷蔵庫と違います。

現状 `lib/types.ts` は `LOCATIONS = ["冷蔵", "冷凍", "常温"]` の 3 区分ですが、
実機の区画は 5 つあり、扉を開けたときの実物と名前が一致していません。

| 区画 | 温度帯 | 入れるもの |
|---|---|---|
| 冷蔵室(まるごとチルド)278L | 約 2℃・高湿度 | 乳製品・卵・豆腐・惣菜・作り置き。ラップなしでも乾燥しにくい |
| 氷温ルーム | 約 -2〜0℃ | **肉・魚**。凍らせずに冷蔵より長持ち |
| うるおい野菜室 103L | 約 4〜8℃ | 野菜・果物。葉物と大物は下段 |
| 冷凍室 137L(3段・まんなか) | 約 -18℃ | 4 日以上先に使う肉魚、冷凍弁当。急速冷凍あり |
| 常温 | — | 未開封の調味料・乾物。じゃがいも・さつまいも |

**判断ルール**

- **冷蔵室が約 2℃と低いため、野菜を冷蔵室に入れると低温障害を起こす。** 野菜は必ず野菜室へ
- 肉・魚は「**3 日以内に使う → 氷温ルーム / 4 日以上先 → 冷凍室**」で切り分ける
- きゅうり・なすなど水分の多い野菜は冷凍しない(解凍時に水っぽくなる)
- 温かいものは約 50℃ まで冷ましてから入れる

**影響しそうな箇所**: `lib/types.ts` の `LOCATIONS`、`components/InventoryScreen.tsx`
のタブ、`components/MoveToInventorySheet.tsx` の売り場 → 場所の推測、`lib/help-content.ts`
の説明文(3 区分前提の記述が 2 箇所)、および Supabase 側の `inventory.location` の
CHECK 制約。既存データの振り分けも必要です。

出典: [まるごとチルド(日立)](https://kadenfan.hitachi.co.jp/support/rei/q_a/a153.html) /
[各室の保存食品(日立)](https://kadenfan.hitachi.co.jp/support/rei/q_a/a139.html) /
[R-HWC54Y 仕様](https://kakaku.com/item/J0000049778/spec/)
