# しくみ ― このアプリが中で何をしているか

**読む人**: 半年後の自分。プログラミングの用語をほとんど知らない前提で書く。
**目的**: 中身が「触ると何が起きるか分からない箱」にならないようにする。

- 使い方(操作方法)は **アプリの中**。ホーム右上の「使い方」、または買い物タブの「⋮」→「使い方」。
  文面の実体は [lib/help-content.ts](../lib/help-content.ts) 1ファイルだけ。
- 環境を新しく作り直す手順は [セットアップ手順.md](セットアップ手順.md)。
- 何を作るつもりだったかは [設計書.md](設計書.md)。
- この文書は「**なぜそう作ったか**」と「**どこを触ると何が壊れるか**」。

---

## 1. 一言でいうと

**スマホの中にデータの写しを持ち、余裕のあるときにサーバへ送る Web アプリ。**

普通の Web サイトは「押す → サーバに聞く → 返事が来たら画面が変わる」。
このアプリは「押す → **その場で画面が変わる** → あとで裏でサーバに送る」。

理由はひとつ。**スーパーの店内は電波が悪い**から。
チェックを押すたびに数秒固まるリストは、2回目から使われなくなる。

この判断がアプリ全体の形を決めている。以降の複雑さはほぼ全部この一点から来ている。

## 2. 全体の絵

```
   夫のスマホ                         Supabase(クラウド)                妻のスマホ
┌──────────────┐                  ┌────────────────────┐          ┌──────────────┐
│ 画面(React)  │                  │  Postgres          │          │ 画面(React)  │
│    ↕         │                  │  ・テーブル約30    │          │    ↕         │
│ ストア       │ ←── 送信 ────→   │  ・RLS(見える範囲)│ ←──→     │ ストア       │
│  (lib/*.ts)  │ ←── 通知 ────    │  ・Realtime(通知) │          │  (lib/*.ts)  │
│    ↕         │                  │  ・Auth(ログイン) │          │    ↕         │
│ IndexedDB    │                  └────────────────────┘          │ IndexedDB    │
│ (端末内の写し)│                                                  │              │
└──────────────┘                                                  └──────────────┘
        ↑
   Service Worker(画面の見た目そのものをキャッシュ)
```

登場人物は4つ。役割が全部違う。

| 名前 | 何者か | 何を持っているか |
|---|---|---|
| **画面** | 見えている部分 | 何も持たない。ストアに聞いて表示するだけ |
| **ストア** | 司令塔 | 今のデータ・未送信の行列・通信中かどうか |
| **IndexedDB** | 端末内の保管庫 | データの写しと「まだ送れていない操作」 |
| **Service Worker** | 画面の材料の保管庫 | HTML/CSS/JS。**データは持たない** |

> **よくある混同**: 「オフラインで開ける」と「オフラインでデータが見える」は別物。
> 前者は Service Worker、後者は IndexedDB の仕事。両方ないと成立しない。

## 3. チェックを1回押すと何が起きるか

一番大事な流れ。ここだけは順番まで覚えておく価値がある。

```
① 指が触れる
     ↓ 0秒
② 画面が即座に「済」になる          ← ここでユーザーの体験は完了
     ↓
③ IndexedDB に「済にした」と書く    ← アプリを閉じても消えない
     ↓
④ 未送信の行列(outbox)に積む
     ↓
⑤ 電波があれば Supabase に送る
     ↓
⑥ Supabase が相手のスマホに通知(Realtime)
     ↓
⑦ 相手の画面にも「済」が出る
```

**②で完了しているのが肝心。** ⑤以降が失敗しても、遅れても、体験は壊れない。

電波がなければ④で止まる。行列は端末に残る。電波が戻ったとき・アプリを再び開いたとき・
画面を表に戻したときに、⑤から自動で再開する。

実装: [lib/store.ts](../lib/store.ts) の `toggle()` → `queue()` → `flush()`。

### 送信に失敗したとき、どう見分けるか

ここが一番の落とし穴だった。失敗には2種類ある。

| 種類 | 例 | 正しい対応 |
|---|---|---|
| **一時的** | 電波が弱い、圏外、サーバが混んでいる | **行列に残す。** あとで必ず再送 |
| **恒久的** | その行はもう存在しない、権限がない | **捨てる。** 何度送っても同じ |

これを間違えると、電波が弱いだけの操作を「もう無理」と判断して捨ててしまう。
店内でチェックした10個が家に着いたら消えている、という最悪の壊れ方をする。

判定は [lib/store.ts](../lib/store.ts) の `isPermanent()` に集約してある。

```ts
// エラーに「意味のあるコード」が付いているか?
// 付いていない = ネットワーク層で死んだ = 一時的 = 残す
```

> **実測して分かったこと**: 通信そのものが失敗したとき、Supabase のライブラリは
> `code: ""`(空文字)・`status: 0` を返す。`code` が文字列かどうかで判定していると
> 空文字も「コードがある」と見なされ、**電波の弱い操作が全部捨てられる**。
> node_modules の中を読んで初めて分かった。推測では絶対に見つからない類のバグ。

### 2人が同時に触ったとき

| 状況 | ルール | なぜ |
|---|---|---|
| 片方が済、片方が未 | **済が勝つ** | 買ったものが未購入に戻ると、また買ってしまう。逆は「もう1回チェックする」だけ |
| 同じものを2人が追加 | **止めて確認を出す** | 牛乳が2本並ぶより、聞かれるほうがまし |
| 数量が食い違う | **あとの操作が勝つ** | 単純な上書きで困らない |

### データの扱いが2種類ある理由

| 方式 | 使う場所 | 特徴 |
|---|---|---|
| **ストア**(store.ts / inventory-store.ts) | 買い物・在庫 | オフラインで書ける。未送信の行列を持つ。**作るのが大変** |
| **useTable**(use-table.ts) | 予定・家計・レシピ | オフラインでも**見える**が、書くのはオンラインのみ。**軽い** |

全部をストア方式にしなかったのは意図的。
店内でチェックするのは買い物リストだけで、予算をオフラインで編集したい場面は現実にない。
複雑さは必要な場所にだけ置く。

## 6. 誰が見られるか(RLS)

### 仕組み

Supabase の鍵(`NEXT_PUBLIC_SUPABASE_ANON_KEY`)は**アプリのソースに埋まっていて、誰でも読める**。
これは設計ミスではなく、そういう前提の鍵。

守っているのは **RLS(Row Level Security)** という Postgres の機能。
「ログインしている人が `household_members` に載っている世帯の行だけ返す」という規則を、
**データベース側**に書いてある。アプリ側のチェックではないので、アプリを迂回されても効く。

だから正しい確認方法はひとつ:

> **鍵だけを使って(ログインせずに)データを取りに行き、`[]` が返ってくるか。**

実際に本番のデータを入れた後で全テーブル・全ビューについて確認済み。
読みは `[]`、書きは `401` / `42501` で拒否される。

### 一度ここが破れていた(記録として残す)

`v_monthly_by_category` と `v_cost_per_meal` の2つのビューは、
**RLS を素通りして家計データを誰にでも返していた。**

原因: Postgres のビューは既定で「作った人の権限」で動く(`security definer` 相当)。
中の表に RLS があっても、ビュー越しなら効かない。

修正: [06_patch_views_rls.sql](../supabase/06_patch_views_rls.sql) で `security_invoker = on` を付けた。
これで「呼んだ人の権限」で動くようになり、RLS が効く。

**教訓**: 表に RLS を付けても、**ビューには別途対応が要る**。
今後ビューを増やしたら必ず `security_invoker = on` を付ける。

## 7. 触るときに知っておくべき14個の癖

| # | こと | 気をつけること |
|---|---|---|
| 1 | Service Worker は古い画面を配り続ける | 画面を変えたら [public/sw.js](../public/sw.js) の `VERSION` を必ず上げる。上げ忘れると更新が届かない |
| 2 | 新しいページを足したら | `sw.js` の `APP_SHELL` にも足す。でないとオフラインで開けない |
| 3 | IndexedDB の構造を変えたら | [lib/local-db.ts](../lib/local-db.ts) の `DB_VERSION` を上げる |
| 4 | キャッシュを空にしてはいけない | 昔 `writeCache(表, [])` としていて、オフラインで「全部消えた」ように見えた。今は「古い印」を付けるだけ([lib/table-cache.ts](../lib/table-cache.ts)) |
| 5 | 削除は条件付きで書かない | `delete().eq("status","未購入")` のような条件を足すと、別経路の削除が空振りして行が復活する。`force` で明示的に外す |
| 6 | 保存は1回にまとめる | 数量・期限・場所を別々に保存すると、あと勝ちで打ち消し合う。`saveDetails()` が1回の更新にまとめている |
| 7 | ログイン切れで画面を消さない | 401 が来ても、行列は保持してリストは出したまま、上に帯を出す。消すと未送信の操作が死ぬ |
| 8 | セッション確認は待ち続けない | 電波が悪いと `getSession()` が返らない。3秒で打ち切る。**打ち切りをログアウト扱いにしない**(1回やって圏外でログイン画面に落ちた) |
| 9 | `backdrop-blur` の下で `fixed` は効かない | ぼかしを持つ要素は「位置の基準」になってしまう。メニューの覆いはヘッダーの外に置く |
| 10 | **秘密をタグの行に持たせない** | 見える/見えないの判定は `events.private_owner_id`(予定の行)だけを見る。タグを見に行く実装にすると、タグを1つ消した瞬間に隠していた予定が全部相手に出る(外部キーの `on delete set null` は RLS を通らないため)。設計で一度これを踏んでいる |
| 11 | **キャッシュは利用者ごとに分ける** | IndexedDB のキーに利用者を混ぜてある([lib/local-db.ts](../lib/local-db.ts) の `setCacheScope`)。ここを戻すと、端末を2人で使ったとき前の人の非公開予定が次の人に出る |
| 12 | **新しいページには必ず `RequireSession`** | ログインの確認は共通部品にしてある。1画面でも素で置くと、そこから中身が見えてしまう |
| 13 | 漢字とかなは自動では結びつかない | 「たまねぎ」と「玉ねぎ」は文字として別物。[lib/matching.ts](../lib/matching.ts) の `SYNONYMS` に手で登録している。**新しい言い換えは表に足す** |
| 14 | **「また買う」の印を2つ作らない** | 切らしたら買い足す印は `pantry.staple` **だけ**。在庫の表に別の列を足すと、アプリは「足りない」・[scripts/restock-staples.mjs](../scripts/restock-staples.mjs) は「足りている」と判断がずれる。足す側も両方が「未購入の同じ品」を見て飛ばすので二重にならない |

## 8. 実際に踏んだ罠(同じ穴に落ちないために)

コードを読んでも分からない、**動かして初めて分かった**もの。

| 何 | どう気づいたか | 教訓 |
|---|---|---|
| ビューが RLS を素通り | 鍵だけで叩いたら家計データが返ってきた | **実際に叩く**。設定画面が緑でも意味がない |
| 電波が弱いと操作が消える | ライブラリの中身を読んだら `code:""` を返していた | 外部ライブラリのエラーの**形**は推測しない |
| 保有銘柄が12件中3件しか出ない | 実データを入れて画面を見た | 「最新の日付」で絞ると、記録日が違う口座が落ちる。**銘柄ごとの最新**が正しい |
| 通信断でログイン画面に落ちる | 自分で書いたテストが落ちた | 直したつもりの修正が**別の壊れ方**を作る。直したら必ず再テスト |
| 「たまねぎ」で「玉ねぎ」が出ると思い込んでいた | テストを書いたら出なかった | **動かす前の説明は仮説**。仮説を事実として書かない |

### 非公開の予定を作ったときの記録(3回目の点検)

「タグで非公開にする」を実装する前に、**3体のエージェントに“夫の鍵で妻の非公開予定を覗け”と指示して**
設計を壊しにいかせた。全部コードで裏を取ったうえで、次が実在した。

| 見つかったもの | なぜ危なかったか |
|---|---|
| **タグを1つ消すと秘密が全部出る** | `events.tag_id` は `on delete set null`。外部キーの set null は RLS を通らずに実行されるので、タグを消した瞬間に「タグ無し = 秘密ではない」と判定され、件名も場所もメモも相手に出る。**攻撃ではなく普通の操作が引き金**。秘密を予定の行(`private_owner_id`)に焼き付けて解決した |
| **エラーの種類で存在が数えられる** | 見えない予定にコメントを投げると RLS 違反(42501)、存在しない予定だと外部キー違反(23503)。id は連番なので、順に投げてコードを見るだけで「相手の非公開予定の id 一覧」が手に入る。判定の既定値を「隠す」に倒して、両方同じエラーにした |
| **タグ名の重複エラーで名前が当たる** | 一意制約の検査は RLS を迂回する。「通院」という公開タグを作ろうとして重複エラーが出れば、相手が「通院」という非公開タグを持つと分かる。一意索引を公開用と非公開用の2本に割った |
| **端末のキャッシュに残る** | RLS が完璧でも、`useTable` は取った行を IndexedDB に丸ごと置き、しかも**ログイン確認より先に描く**。妻がサインアウトした端末で夫が予定を開くと妻の行が出た。`clearCache()` は書いてあったのに**一度も呼ばれていなかった** |
| **`/plan` にログインの確認が無かった** | 確認は買い物リストの中にしか無く、ほかのタブは素通り。上のキャッシュと合わせると、端末を拾った誰でもログイン画面を経ずに予定を読めた |

**塞げていないものも書き残してある**([11_schema_v5.sql](../supabase/11_schema_v5.sql) の C-6)。
id の連番から件数と作られた時期が推測できること、削除の通知が RLS を通らないこと、
件数の概算が漏れること。**「何の予定かは絶対に分からない」ことは守れているが、
「予定があること自体」は完全には隠せていない。** 隠せていないものを隠せているつもりにしない。

### 全体を通しての教訓

多エージェントで3回の点検をかけ、計70件近い指摘を得た。ただし:

> **指摘の多くは、1回目の修正が生んだ副作用だった。**
> そして指摘の一部は、コードを読むと既に的外れだった。
> **必ずコードで裏を取ってから直す。** 指摘をそのまま信じない。

## 10. 用語の小辞典

| 言葉 | 意味 |
|---|---|
| **PWA** | ホーム画面に置けて、アプリのように開く Web ページ |
| **Service Worker** | 画面の材料を端末に貯めておく係。オフラインで開けるのはこれのおかげ |
| **IndexedDB** | ブラウザの中の保管庫。閉じても消えない |
| **outbox(未送信の行列)** | まだサーバに送れていない操作の待ち行列 |
| **Supabase** | データベース+ログイン+通知をまとめて借りているサービス |
| **RLS** | 「この人にはこの行だけ見せる」というデータベース側の規則 |
| **Realtime** | 相手が変えたら自分の画面にも届く通知の仕組み |
| **楽観的更新** | サーバの返事を待たずに先に画面を変えること。このアプリの土台 |
| **ビュー** | 表そのものではなく「表を計算した見え方」。RLS に別途の対応が要る |
| **Vercel** | GitHub に push すると自動で公開してくれるサービス |

## 11. まだ無いもの(できているつもりにしない)

| 何 | いまどうなっているか |
|---|---|
| **予定の通知** | **入れないと決めた。**欄そのものを画面から外した。PWA は閉じている間に決まった時刻で鳴らす手段を持たず、本当に鳴らすにはサーバから Web Push を送る仕組み(鍵の発行と、時刻を見て送る常駐処理)が要る。選べるのに何も起きない欄は「鳴ると信じて準備しない人」を作るので、置かないほうがよいと判断した。`events.notify_min` 列は残してある |
| **配当の入金記録と「旅行に使える配当」** | **まだ無い。**入っているのは `watch_history.dividend`(1株配当の**予想値**)と `screening_candidates` の見込みだけで、**実際にいくら入金されたかはどこにも残っていない**。累計を出して「旅行までいくら」を見せるには、受取1件ずつの表と、再投資に回すぶんと旅行に回すぶんの決めごとが要る。その決めごと(累計が目標額に届いたら使う / 年間配当が目標を超えたら以後を使う / 毎年の一部を回す)がまだ決まっていないので、表を先に作っていない |
| **予定の並べ替え** | やることの `sort_order` は列だけ用意してあり、指で並べ替える操作は無い。期限順に自動で並ぶ |
| **ノート・日記** | Lifebear にはあるが、今回は入れないと決めた |
| **クラウドからのチャット** | Cowork をクラウドで動かすと Supabase に届かない。出られる宛先が決められていて、Supabase も Vercel も入っていない。宛先の追加は Team / Enterprise プランにしかない。**読むだけなら jisui\いまの状況.md を読む(見張りが5分ごとに書き出す)。全部を直接やるならタスクの「…」→「お使いのコンピュータに移動」**。中継APIを Vercel に置く案も試したが、Vercel 自体が同じ壁に阻まれる |
| **予定があること自体を隠す** | 件名は隠せているが、id の連番・削除通知・件数の概算から「何件あるか」は推測できる。[11_schema_v5.sql](../supabase/11_schema_v5.sql) の C-6 に詳しく書いた |

## 11. AI(Cowork)との関係

**アプリの中に AI 機能は入れていない。** API の従量課金を避けるため。

代わりに、Cowork(サブスク)から Supabase を直接読み書きするスキルを
`C:\Users\mmizu\.claude\skills\jisui\` に置いてある。

| ファイル | 役割 |
|---|---|
| `SKILL.md` | 何ができるか。Cowork はこれを読んで判断する |
| `KAKEIBO.md` | 家計まわりの作法(費目の決め方など) |
| `db.py` | 実際に Supabase を読み書きする道具 |
| `.env` | 接続先とログイン情報。**共有しない** |

「今週の献立を考えて」「先月の食費は」といった相談はここが受け持つ。
アプリは記録と閲覧に徹する、という役割分担。
